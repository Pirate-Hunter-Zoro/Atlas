# upkeep/opencode: the OpenCode parity layer

Gives DeepSeek inside OpenCode (1.19.5) the long-running harness tools: wakeups, cron, background shells, monitors, background agents, forks, workflow scripts, worktrees, notifications.

`python3 upkeep/opencode/install.py [--dry-run] [--home DIR]` installs it into `~/.config/opencode`. Exit status is the number of problems. `upkeep.py run` calls it; it is idempotent. Tests: `python3 -m unittest upkeep/opencode/test_install.py upkeep/opencode/test_parity.py` (the second runs the plugin under node with a stub client).

| File | Installed as | Role |
| --- | --- | --- |
| `plugins/parity.ts` | `~/.config/opencode/plugins/` | Every tool, the guards, the capabilities prompt and the Playwright browser MCP. It must export only `ParityPlugin`, because OpenCode calls every exported function as a plugin |
| `agents/*.md`, `commands/*.md` | same names | `worker`, `fixer` and `structured` on flash; `deep`, `reviewer` and `verifier` on v4-pro. `reviewer`, `verifier` and `structured` deny the edit tools by permission. `reviewer` and `verifier` share one bash rule set. Its first rule is `"*": deny`, because the last matching rule wins. It allows commands that cannot write or run code whatever their arguments, git's read subcommands without `--output` or `--ext-diff`, one test file per `python3 -m unittest`, and `python3 board/test/run.py`. So no `sed`, `rg`, `find`, `sort`, `node` or `git grep`, whose arguments can write or run a program (`git grep -O` runs one), and no `brew bundle` or `mise`, which evaluate a config as code. Two layers hold, in order. First the bash rules: OpenCode matches them against each simple command's literal text and skips `cd`, so quoting (`git log --o''utput=x`) and a redirect on a subshell, group or loop pass them, and they cannot make it read-only. Second the plugin's read-only guard (*Guards*), which covers `reviewer`, `verifier`, `structured` and `explore` by name however they start, and removes quotes and splits on spaces and tabs before it judges. It models bash rather than running it, so neither layer is a sandbox. The bash rules alone hold where no plugin loads, so under `--pure` these two agents can write. `/ultracode` runs on v4-pro through `model:`, with no `agent:` or `subtask:`, because the plugin starts the read budget on the session `command.execute.before` names, and a subtask would end before its workflows report. `/loop`, `/review`, `/simplify` |
| `capabilities.md` | `~/.config/opencode/capabilities.md` | Added to the system prompt by the plugin: the tools, how work is judged, the workflow API and what the user can type. Names tools only, and no vendor outside the path `~/.claude/CLAUDE.md` |
| `config.json` | merged into `opencode.jsonc` | The managed keys. Never copy it into the config dir: OpenCode loads a `config.json` there as config |
| `package.json` | merged into `~/.config/opencode/package.json` | Pins `@opencode-ai/plugin` and `sdk` to the opencode version; bump both with opencode |
| `env` | read by `shell.zsh` | Feature flags. Never `OPENCODE_EXPERIMENTAL=1`: it turns on the unstable code mode |
| `launchd/com.mikeyferguson.opencode-serve.plist` | `~/Library/LaunchAgents/` (by upkeep.py, `@HOME@` filled) | The persistent server on 127.0.0.1:4096. Its env block is `env` plus `PATH` and `PARITY_PRIMARY=1` (a test checks) |
| `shell.zsh` | sourced from the upkeep block in `~/.zprofile` | Exports `env`; `oc` and `ocrun` attach to the server with `--dir "$PWD"`, or run a local opencode when it is down |
| `coder` | `~/bin/coder` | Same attach-or-fallback; keeps the line `exec opencode --auto` the doctor looks for |

The config merge parses JSONC and keeps every unmanaged key. A file that does not parse is reported and left alone. A commented original is saved once as `opencode.jsonc.before-upkeep`, because the rewrite drops comments. The merge deletes the `openrouter`, `groq` and `cloudflare` provider blocks, and drops `plugin` entries for files under `plugin/` or `plugins/`, which load automatically.

Top-level `permission` stays the string `"allow"`, because MO's legacy opencodedoctor resets any other value every minute. `doom_loop` and `external_directory` still default to ask under it, so `agent.{build,plan,general,explore}` and the agent files allow them.

The board's tutor runs `opencode --pure`, which loads no plugins but does read the global config and starts its MCP servers. Everything that only makes sense with the parity tools (the capabilities prompt, the browser MCP) therefore comes from the plugin, not from `opencode.jsonc`. `PARITY_BROWSER_MCP=0` turns the browser MCP off.

Skills under `~/.claude/skills` and `~/.agents/skills` (any directory holding `SKILL.md`) are copied into `~/.config/opencode/skills`. Hidden directories such as `.trash` are skipped, and so is any skill that names a Claude-only surface (`mcp__claude-in-chrome`, the Claude desktop app, Claude's memory). Nothing is ever deleted.

## How the plugin works

- Every job reports by posting a message into the session that started it (`client.session.promptAsync`). The model ends its turn and is woken by `<task>`, `<monitor>`, `<wakeup>`, `<cron>`, `<bg_shell>` or `<workflow>`. This needs a live opencode process, so use the server (`oc`, `coder`). A plain `opencode run` exits after its turn; the server then adopts its jobs, but a subagent it started ends with it.
- State lives in `$PARITY_STATE_DIR`, else `~/.local/state/opencode/parity/`: `jobs.json`, `primary.json`, `shells/<id>.log`, `workflows/<run>/{script.js,journal.jsonl,log.txt,result.json}`, `guard/<session>.json`, `schema/<session>.json`, `bash_env` and `parity.log`.
- Every opencode process that loads the plugin shares `jobs.json`, under a lock. Each job names its owner process, and only the owner arms it. Other processes list it, and delete it from the file; the owner cancels it on its next sync (10 s). When an owner dies, the server (`opencode serve`, or `PARITY_PRIMARY=1`) adopts its jobs; with no server up a TUI does. `opencode run` and other subcommands never adopt.
- An adopted job resumes. Overdue wakeups fire with `late_by`. Monitors are restarted. Background shells are detached, so their exit code file is still seen. Agents report what their child left. Interrupted workflows are announced with their `resume_run_id`.
- A workflow `agent()` with a `schema` sends `format: json_schema` with `variant: "nothink"`, because DeepSeek rejects that tool choice while thinking. `think: true` asks for JSON in text instead and checks it. Opencode 1.19.5 answers 400 ("Expected OutputFormatJsonSchema") to any message listing that reaches a user message carrying a schema, and the TUI may fail to open such a child. So the plugin names each schema prompt's message id itself and records it, with every message of that session from `message.updated` events, in `schema/<session>.json`. Its reads page with `limit` and the `before` cursor and step over each schema prompt, so they never ask for one. A schema child it did not record (one from an older plugin) is read one message at a time; each schema prompt there costs one refused page, after which the read steps over it as the parent of the oldest reply. `session_read` is the reader for these sessions, and `agent_list` marks them; the prompt comes from the run's `journal.jsonl`.
- Built-in `task` with `background: true` (flag `OPENCODE_EXPERIMENTAL_BACKGROUND_SUBAGENTS`) is the normal background subagent. `agent_spawn` covers worktrees and other models, and stands in if the flag goes away.

### Guards

`tool.execute.before` refuses a call by throwing a one-line reason that names the right move. It covers every session, subagents included, and the commands of `bash`, `bg_shell`, `monitor` and workflow `sh()`. A guard that throws refuses the call. Commands are parsed: `;`, `&&`, `||`, `|`, newlines, quotes including `$'...'`, `$(...)`, here-documents and here-strings, `NAME=value` prefixes, wrappers (`sudo`, `env`, `nice`, `time`, `timeout`, `nohup`, `uv run`, `uvx`, `mise exec`, `poetry run`, `pipx run`, `npx`, `bunx`, `pnpm exec`/`dlx`, `npm exec`; their directory options followed, `-c` strings parsed as shell), `xargs` (with `-a`/`--arg-file` files read, `-a` inside a cluster such as `-0a` too), `bash -c`/`eval`/`source`, scripts piped or redirected into a shell or interpreter, `find -exec` (with `{}` as each root), git aliases (including one the same call defines), braces, `cd`/`pushd`/`popd` (with options), and commands inside code (`subprocess`, `os.system`, `child_process`, `system()`, osascript's `do shell script`). A script the call runs is read when it is ad hoc: written by the same call, under a temp directory, or outside every repository. A tracked script in a repository is not re-read, so a model that writes a script into a repository and runs it is judged only by the write.

Every word is unquoted first (single, double, backslash and `$'...'` quoting), and words split on spaces and tabs. Paths given as `~`, `~user` (`/var/root` for root, else `/Users/<user>`), `~+`, `$HOME` and `${HOME...}` in any form, a substitution opening the word that names the home directory (`$(echo ~)`, `$(cd && pwd)`), `$PWD`, `$(pwd)`, `$(git rev-parse --show-toplevel)`, `$(echo ...)`, variables the call assigned (and `read X <<< word`), relative to the directory or absolute are compared case-insensitively with symlinks resolved, including links the same call makes with `ln`. A loop variable, `read` from a pipe, and any other substitution are unknown. A glob is expanded on disk as the shell would. A searcher's pattern (`grep keys.env file`) is not a path. What stays unknown is refused where it matters: a command name the guard cannot resolve (any session), a file a content reader (`cat`, `grep`, `cp`, ...) cannot resolve unless every file it could reach is checked, a write target from the main checkout, a pathspec, and code piped from a command. The parse is a model of bash, not bash: an obfuscation it does not model can pass, so read-only agents run on an allowlist. The rules, first refusal wins:

| Rule | Refuses |
| --- | --- |
| Credentials | Reading, copying, uploading or changing `~/.local/share/opencode/auth.json`, `*.env`, `rclone.conf`, `~/.config/{rclone,media-syncer,api-keys}`, `backup-private/`, SSH private keys and plists whose keys name a key, token or secret, in any user's home. `defaults` naming such a plist without `.plist`, by path or domain, and `rclone config show`/`dump`. Inline code (`python -c`, `node -e`/`-p` and clusters such as `-pe`, `perl`/`ruby -e`, a here-document or script fed to them) that names one by a path segment, file name or glob (`opencode` with `auth.json`, `id_ed25519`, `.ssh`, `keys.env`, a `.env` name, `'*.env'`, `rclone`, `media-syncer`, `backup-private`, `dotenv`, `loadEnvFile`), however it builds the path. Env loaders, matched by name (best-effort): the `dotenv`, `dotenvx` and `env-cmd` commands, and a module an interpreter runs or preloads (`python3 -m dotenv`, `node -r dotenv/config`, `--import`, `ruby -r`, `NODE_OPTIONS`). The grep and glob tools over a credential location, or over a tree holding a `.env` file ripgrep would read (one its own work tree does not ignore, nested repositories and submodules included) that the pattern can match. A recursive reader (`grep -r`, `rg`, `tar c`, `rsync`) has every file below its paths walked, narrowed by `--include`/`-g`, and is refused past 20,000 entries. Words from `$(find ...)`, `$(ls ...)` or a lister (`ls`, `find`, `git ls-files`, `grep -l`) piped into `xargs` are checked by walking the lister's roots, with globs expanded against the directory (`ls *.env | xargs cat`), and so are the commands of a shell xargs runs (`xargs -I{} sh -c 'cat {}'`). An interpreter given a lister's names, through `xargs` or on stdin (`ls *.env | xargs python3 -c ...`, `ls | python3 script.py`), is refused when the lister's roots hold a credential, whatever its code does; one fed names by any other command is not checked. `launchctl print`/`list` of a job whose plist holds keys, `launchctl export`, and `ps` showing environments (`ps eww`, `-E`). Names-only commands (`ls`, `test`, `stat`, `echo`, `git status`/`check-ignore`/`ls-files`) pass |
| Command name | A command name that is a variable or substitution the guard cannot resolve (`$CMD`, `$(cat f)`), in any session |
| Read-only | For agents named `reviewer`, `verifier`, `structured` or `explore` (however started) and workflow `agent(prompt, {readonly: true})`: edit, worktree and agent-starting tools; a write it detects outside `/tmp` (redirection, `tee`, `cp`, `mv`, `rm`, `sed -i` and sed's `w`/`W`/`e` and `s///w`, `sort -o`, `uniq a b`, git `--output`, `format-patch`, `archive -o`, `bundle create`); `find` with `-delete`, `-exec`, `-execdir`, `-ok`, `-fprint` or `-fls`; and any program off an allowlist of read commands. Wrappers are looked through, so `uv run python -m unittest` runs the test and `python3 -I script.py` runs the script. Allowed: readers and searchers, git's read subcommands without `-c`, `--output`, `--ext-diff`, `--textconv` or a pager (`git grep -O`, `--open-files-in-pager`, abbreviations included), `sqlite3` reads without dot-commands (`-cmd`, `-init` and SQL piped in from `echo`, `printf` or a here-document included), `curl` without a body, upload or `-o`, `gh` that neither downloads nor clones, `make -n`, formatters in check mode, `python3 -m unittest`/`pytest`/a file under `test/`, `node --test`, syntax checks, and inline `-c`/`-e` code that neither writes, runs a program, nor hides a call (`eval`, `getattr`, `__import__`, string-built names). Tests from `/tmp`, scripts, `ln`, `osascript`, editors and variables such as `GIT_PAGER` or `NODE_OPTIONS` are refused |
| Worktrees | A write it detects under `~/Developer/Atlas/board/`, from any session: named targets with globs expanded and links followed, `git checkout -f/--discard-changes/restore/stash/reset --hard/clean/rm/mv/apply/am/cherry-pick/revert/rebase/read-tree -u/checkout-index` and branch switches in the main checkout, and `patch`, archive extraction, `find -delete`, `make`, formatters (`python3 -m black` too) on paths or a directory that covers `board/`, `npm`/`pnpm`/`yarn`/`bun` installs run in or pointed at `board/` (`--prefix`, `-C`, `--dir`, `--cwd`), and code whose reach covers `board/`. Code that writes to a path built from the home directory (`Path.home() / ...`, `.joinpath(...)`, `Path(Path.home(), ...)`, `os.path.expanduser('~')`, `os.homedir()`, `HOME` from the environment) or from an absolute or `~/` literal (`os.path.join('/abs', 'board', 'x.py')`, `Path('/abs', ...)`, `Path('/abs').joinpath(...)`, `'/abs' + '/board/x.py'`, node's `path.join`/`path.resolve`; raw `r'...'` strings and JS templates without `${}` included) is judged by the path it builds, when the parts are literals. Code that writes and holds a literal base covering `board/` plus a literal for the rest, joined any other way (`'/'.join`, `%`, `.format`, an alias of `join`), is judged as if joined. pandas `to_csv` and kin, `np.save`, `savefig` and any `.save(...)` count as code writes. Code that removes or moves a whole tree (`shutil.rmtree`/`move`, `os.rename`/`replace`, a recursive `fs.rm`) is refused on a literal path holding `board/`, as `rm -r` is. A path held only in a variable is best-effort. Code that writes from a directory covering `board/` passes only when its literals, home-built paths included, name paths outside it and no other path is computed. From the main checkout a write target the guard cannot resolve is refused, a home-built path ending in a non-literal part included. `git merge`, `git pull` and `git checkout main` there pass: that is how main changes |
| /ultracode tree | In an `/ultracode` session, and in every subagent or workflow agent it starts (five parents up): an edit tool, or a named shell write target, inside a repository's main checkout (a directory whose `.git` is a directory). A linked worktree (`.git` is a file), `/tmp` and paths in no repository pass, and so do git's own commands (`git merge` there is how main changes). Code that writes and paths held in variables are not checked |
| polling | A session with a background job of its own (a workflow, monitor, `bg_shell`, agent or wakeup): a `bash` call that only sleeps (`sleep`, with at most `echo`, `printf`, `true`, `date`), and a fourth waiting call in one turn (`wakeup`, `cron_list`, `cron_delete`, `agent_list`, `bg_output`). The job reports as a message, so the model ends its turn; a new message starts a new count |
| Staging | `git add -A`/`--all` (and its abbreviations)/`-u` without paths, a pathspec naming the whole repo (`.`, `*`, `**`, `:/`, exclusions only, a pattern with no literal name, the root's own path), one the guard cannot resolve, `--pathspec-from-file`, `xargs git add` from a pipe, `git commit -a` or `git commit .`, in any repo |
| Self-prompt | Posting into a session through the server's session API from the shell (any host on port 4096, any HTTP client or code), or `opencode run --session` |
| Commit gate | `git commit`, `merge`, `pull`, `cherry-pick`, `am`, `revert`, `rebase`, `push`, a fetch into a local branch, `branch -f`, `checkout -B`, `update-ref`, `commit-tree`, `reset` to another commit (aliases, code and ad hoc scripts that run them included), `save-and-push.sh`, `ship.sh`, `board push`, `gh pr merge`, a merging `gh api` call and `opencode run`, while a run in the session, an ancestor or a descendant holds a `fail` that no later round of its own `verify_until_pass` call passed and no run started after it arrived has re-verified by returning (for a descendant's fail, a run on the path from it to the committing session). A run is a workflow run or one finished reply of a `verifier` or `reviewer` subagent started outside a workflow. A descendant of an ancestor holds the committing session too when that ancestor started the committing session's branch after the fail arrived. An owner sentence saying "ship over it" in the session holding the fail lifts it, and for a descendant's fail so does one in the committing session or the session where the two chains meet, unless it is a question or a negation; text the plugin sent never does |
| Read budget | In a session started by `/ultracode`, a sixth read-type call (`read`, `grep`, `glob`, `bash`, `bg_shell`, `monitor`, `bg_output`, `session_read`, ...) before a `todowrite` of two steps or more. Its subagents are not counted |

Only verdicts verify agents produced lift the gate. A read-only agent's verdict is its `verdict` field or, for a text reply (no `schema`), its first non-blank line when that starts with `PASS` or `FAIL` (`PASSED` and `FAILED` too, any case, `Verdict:` before it allowed), with the rest of the reply as its reason. Markdown on that line is read through (heading and quote marks, `*`, `_`, backticks), and a first line that is only `Verdict` hands over to the next non-blank line. A verify agent whose reply names no verdict, or that does not finish, counts as a `fail`. So does an `agent: "verifier"` or `"reviewer"` doing either in any phase outside a fix stage, though its pass outside a verify phase lifts nothing. Any other read-only agent's reply without one counts as nothing. `verify_until_pass` counts a verdict read from text, and that fail, in its round whether or not the verify stage returns the reply. A verify agent is read-only (`agent: "verifier"`, `"reviewer"` or `"structured"`, or `readonly: true`; never a `worker`, `fixer` or `build` agent), started live inside a phase whose name starts with verify (hyphens and underscores read as spaces) or inside `verify_until_pass`'s verify stage, never its fix stage. Its brief is not judged: it cannot change a file. A verify agent always runs live, so a resumed run never replays its verdict from the journal. A pass from anywhere else (the script's own return value, any other agent's report) is ignored and lifts nothing. A fail counts from any read-only agent outside a fix stage, whatever the phase and whether or not the journal replayed it, and from the finished run's result. Each verdict is saved to `guard/<session>.json` the moment it returns, so it stands if the script then throws, is cancelled or crashes, and whether or not the script returns it. Each `parallel()` thunk and each `verify_until_pass` stage keeps its own phase and round, so units run side by side never change what each other's agents count as; two branches of a bare `Promise.all` share one phase. A fail stands until a later round of the same `verify_until_pass` call passes, or until a workflow run started after it arrived returns with verify verdicts, which then decide (a resume is a new run). A run that throws, is cancelled or crashes, or is still going, decides nothing over another run's fail; its own fails hold. A later phase, unit or `verify_until_pass` call never replaces it, and neither does a run started before it arrived, such as another unit's background run, however late that run's pass comes. A run with no verify verdict changes nothing. A `verifier` or `reviewer` subagent started outside a workflow (the `task` tool, `agent_spawn`, `agent_send`, an @ mention) records each reply it finishes as one returned run in its parent session's verdicts, started when it was prompted. Its verdict is read as above, and a reply naming none, or a turn that ends in an error, is a fail. The reply is read when the session goes idle or when the `task` tool returns, whichever comes first, and the gate waits for a reply being read. A session with no parent records nothing, and a workflow's own agents are judged by the workflow. `result.json` (as `verify_verdicts`) and the `<workflow verdict="...">` message carry the run's standing verdicts. The gate holds while the committing session, an ancestor, or a descendant has a run holding a fail. A descendant is a session among those with verdicts in `guard/` (each file names its session) whose chain of up to five parents reaches the committing session. A descendant of an ancestor holds it too: the meeting point is the nearest session of the committing session's chain that the other chain reaches, and the committing session is held when the meeting point started its branch (the meeting point's child on the committing session's chain) after the fail arrived. Each parent and creation time is the one the plugin recorded when it started the session, else the client's `parentID` and `time.created`, asked once per process (an error reads as no parent; an unknown time counts as after the fail). A descendant's fail is decided by the same newest-run rule across the tree: a returned run that produced verify verdicts, started after the fail arrived, in the descendant or on the path from it through the meeting point to the committing session. A sibling's run never decides it, and neither does a run started before the fail arrived. This lets the parent re-verify, since a finished subagent cannot run again. So a subagent's own pass never lifts its orchestrator's fail, and a workflow a worker or task subagent ran holds every session above it. A sibling's fail holds neither a sibling that existed before it arrived nor that sibling's children, so a held session cannot ship through a subagent it starts afterwards. A failed one is quoted by its area, reason and defects (`area`, `reason`/`summary`, `defects[].what` and the like), never by the tail of its JSON.

The config hook sets `shell` to `/bin/bash` unless the config names one (`PARITY_BASH=0` skips it), and `shell.env` points `BASH_ENV` at `bash_env`, which turns pipefail on in the tool's shell and unsets itself so scripts it runs are untouched. Under a zsh shell the bash tool's description says so instead.

OpenCode 1.19.5 (`Instruction.systemPaths`) loads the first that exists of `~/.config/opencode/AGENTS.md` and `~/.claude/CLAUDE.md`, then, for the first of `AGENTS.md`, `CLAUDE.md` and `CONTEXT.md` found anywhere from the session directory up to the worktree root, every file of that name on the way. `OPENCODE_DISABLE_CLAUDE_CODE` (set in `env`) or `OPENCODE_DISABLE_CLAUDE_CODE_PROMPT` drops both `CLAUDE.md` entries, and `OPENCODE_DISABLE_PROJECT_CONFIG` skips the walk. With `CLAUDE.md` dropped, the system transform appends the nearest `CLAUDE.md` when the walk finds no `AGENTS.md`. With the walk skipped, it appends the nearest `AGENTS.md`, else `CLAUDE.md`.
